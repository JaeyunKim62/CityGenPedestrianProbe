# 피드백 신호 체계 계획

상태: 제안 단계, 일부 구현 착수
작성: 2026-08-20
관련 문서: `ModularImplementationAndExperimentPlan.md`, `NonvisualSpatialCognitionDesignSpace.md`

목표: "언제 신호를 주는가", "무엇으로 구분되는가", "동시에 울리면 어떻게 되는가"를 모듈마다 따로 정하지 않고 하나의 공통 체계로 정의한다.

## 1. 결론

`NonvisualSpatialCognitionDesignSpace.md` §6은 피드백을 여섯 축으로 분해했고, `ModularImplementationAndExperimentPlan.md`는 모듈을 어떻게 켜고 끄는지를 정했다. 그러나 **신호 자체의 문법**은 어느 문서에도 없다. 현재는 `SemanticAudioGuide` 한 클래스 안에 암묵적으로만 존재한다.

두 번째 피드백 모듈에 소리를 붙이는 순간 이 공백이 문제가 된다. 스위프 모듈은 아직 무음이므로 **지금이 체계를 정할 마지막 시점**이다.

이 문서는 8개의 제안(P1–P8)으로 구성된다. 각 제안은 선택지와 권장안, 그리고 권장하지 않는 안을 배제한 이유를 함께 기록한다.

## 2. 현재 상태 진단

### 신호 정의와 표현이 분리되어 있지 않다

오디오를 다루는 파일은 `SemanticAudioGuide.cs` 하나뿐이고, 그 안에 다섯 층이 함께 있다.

| 층 | 상태 |
| --- | --- |
| 감지 | `semanticMap`을 직접 질의 |
| 트리거 정책 | `StableSeconds`·`EventCooldown`·`ApproachRadius`가 `const`, Inspector에서도 못 바꿈 |
| 신호 정의 | 주파수·길이가 `Awake` 안의 리터럴 |
| 표현·재생 | `AudioSource` 생성·공간화·위치 배치 |
| 로깅 | 사건만 기록, 실제 발화 여부는 기록하지 않음 |

`FeedbackModule` 계약도 표현에 대해 아무것도 말하지 않는다. 새 모듈이 소리를 내려면 `CreateSource`/`CreateTone`을 복사해야 한다.

### 감지 층은 이미 잘 분리되어 있다

`SpatialRayProbe.cs`는 원하는 형태다. `RayBoundaryProbe`는 `MonoBehaviour`가 아니고 도시 구현을 모르며 EditMode에서 검증된다. **신호 층도 같은 패턴을 따른다.**

`ISpatialProbeObservationSink`는 계약과 분배 경로까지 있으나 구현체가 없다. 표현자를 꽂을 자리가 뚫려 있고 비어 있는 상태다.

### 구분되지 않는 신호

| 문제 | 근거 |
| --- | --- |
| 정체성을 주파수 하나로만 구분 | 440 / 1200 / 660-880 / 110 Hz 순음 |
| 순음은 방위 정위가 나쁨 | HRTF 스펙트럼 단서가 없어 ITD에만 의존 |
| 같은 클립이 두 의미로 쓰임 | 진입음과 접근음이 동일 클립, 위치만 다름 |
| 진입음의 방향이 정의되지 않음 | 청취자 위치에 `spatialBlend=1` 음원을 배치 |
| 거리를 음량과 반복간격에 이중 부호화 | 설계 문서 §6 원칙과 충돌 |
| 안전 경고가 별도 채널이 아님 | `HazardPriority`는 내부 우선순위일 뿐 소리로 구분되지 않음 |

가장 혼동되기 쉬운 쌍은 Curb(1200 Hz)와 Crosswalk(880 Hz)다. 피치 축에서 이웃이기 때문이다.

## 3. P1 — 채널 체계: 언제 울리는가

신호를 모듈 단위가 아니라 **역할 단위**로 묶는다. 그래야 모듈이 늘어도 신호 문법이 늘지 않는다.

### 권장: 5채널

| 채널 | 발화 조건 | 시간 구조 | 우선순위 |
| --- | --- | --- | --- |
| `alarm` | study bounds 접촉, Road 진입 | 즉시, 3연타 | 4 |
| `answer` | 사용자가 스위프를 쏜 결과 | 요청 직후 1회 | 3 |
| `transition` | 안정된 semantic 범주 변경 | 사건 발생 시 1회 | 2 |
| `proximity` | 반경 내 다른 범주 접근 | 주기 반복, 간격=거리 | 1 |
| `state` | 현재 위치 유지 | 저강도 장주기 반복 | 0 |

### 배제한 대안

| 대안 | 배제 이유 |
| --- | --- |
| 3채널(`alarm`/`info`/`state`) | `answer`와 `proximity`가 한 채널에 묶이면 능동 질의와 자동 통보를 구분해 분석할 수 없다 |
| 모듈별 채널 | 모듈 수만큼 우선순위 규칙이 늘어 조합 실험에서 관리 불가 |
| 채널 없이 우선순위 숫자만 | 숫자는 로그에서 의미를 잃는다. 채널 이름이 곧 분석 단위다 |

### 핵심 규칙

**`answer`가 주 정보원이고 `proximity`·`transition`은 최소로 유지한다.** 실험 가설이 "능동 샘플링으로 공간 형태를 학습하는가"이기 때문이다. push 신호를 늘리면 사용자가 수동적으로 되고, 설계 문서 §548의 질문("사용자가 지도를 만든 것인지 신호를 따라간 것인지")에 답할 수 없게 된다.

따라서 sweep 조건에서는 기존 `semantic.audio`의 push 신호를 꺼야 비교가 성립한다.

## 4. P2 — 부호화 축 배정: 무엇으로 구분되는가

구분이 안 되는 근본 원인은 한 축이 여러 의미를 나르기 때문이다. 축을 배타적으로 배정한다.

| 지각 축 | 담당 의미 | 금지 |
| --- | --- | --- |
| 음색(배음 구조·거칠기) | **무엇** — 범주 | 거리·긴급도에 쓰지 않음 |
| 짧은 시간 구조(0–0.5초 내 연타 수) | **왜 지금** — 채널 역할 | 범주에 쓰지 않음 |
| 긴 시간 구조(0.25–1.5초 반복 간격) | **얼마나 멀리** — 거리 | 범주에 쓰지 않음 |
| 공간 위치 + 광대역 어택 | **어디** — 방위 | |
| 음량 | 아무것도 부호화하지 않음 | 자연 감쇠와 salience에만 |

시간 축을 두 스케일로 쪼개는 것이 요점이다. 신호 **내부** 패턴이 역할을, 신호 **사이** 간격이 거리를 담당하면 충돌하지 않는다.

### 정위를 위한 규칙

**모든 hit 계열 신호는 짧은 광대역 어택(2–4 kHz 노이즈 클릭)으로 시작하고, 꼬리에 정체성 음색을 둔다.** "어택 = 어디, 꼬리 = 무엇"으로 분리된다. 현재의 순음만으로는 좌우 스위프에서 방위를 들을 수 없다.

### 음량을 정보에서 빼는 이유

설계 문서 §424가 이미 지적했다. 음향 거리 지각과 시스템 감쇠가 혼동된다. 구현에서는 `SignalIntent`에 세기 필드를 두지 않는 방식으로 이 규칙을 **구조적으로 강제한다.** 모듈이 음량을 조절할 수단 자체를 주지 않는다.

## 5. P3 — 영역별 신호 사양

세 가지 후보 세트를 제시한다.

### C-1 음색 분리형

| 영역 | 은유 | 음색 | 대역 |
| --- | --- | --- | --- |
| Sidewalk | 안정된 기저 | 부드러운 삼각파, 배음 2개, 긴 감쇠 | 400–700 Hz |
| Curb | 모서리·전이선 | 대역제한 노이즈 tick, 거의 무피치 | 광대역 |
| Crosswalk | 허용된 통로 | 상승 2연음, 홀수 배음 | 500–1000 Hz |
| Road | 위험 | 저음 + AM 거칠기 | 100–250 Hz |
| Unknown | 미분류 | 무신호 | — |

Curb를 무피치 노이즈로 빼는 것이 핵심이다. 축 자체를 바꾸면 Crosswalk와의 혼동이 원리적으로 사라진다.

### C-2 최소형

hit 여부와 방향만 전달하고 semantic 종류는 부호화하지 않는다. 설계 문서 §128의 권고와 일치한다.

### C-3 음성 라벨형

짧은 단어를 합성음으로 읽는다. 학습 비용이 없지만 지속 청취가 불가능하고 언어 처리 부하가 공간 인지와 섞인다.

### 권장

| 대상 | 세트 |
| --- | --- |
| 스위프 v0(`answer` 채널) | **C-2** — 종류 없이 방향+거리만 |
| 스위프 v1 이후 | **C-1** — 종류를 별도 실험 조건으로 추가 |
| 비교 조건 | C-3은 후보로만 보존 |

C-2를 먼저 쓰는 이유는 각 정보의 효과를 분리하기 위해서다. 방향·거리·종류를 한꺼번에 넣으면 어느 것이 형태 인지에 기여했는지 알 수 없다.

## 6. P4 — 침묵 정책

세 가지 침묵이 현재 구분되지 않는다.

| 침묵 | 의미 | 처리 |
| --- | --- | --- |
| 1 | 미분류 영역에 있음 | 무신호 + 로그 |
| 2 | 스위프를 쐈으나 사거리 내 경계 없음 | **명시적 miss 신호 필요** |
| 3 | 모듈 꺼짐 또는 시스템 정지 | `state` 채널이 생존 신호 역할 |

2번은 설계 문서 §125가 이미 지적한 문제다. miss를 침묵으로 두면 사용자는 "열린 공간"과 "고장"을 구분할 수 없다. 그리고 3번 때문에 `state` 채널을 아주 낮은 강도로라도 유지할 이유가 생긴다.

신호 ID로는 `probe.miss`를 `answer` 채널에 둔다.

## 7. P5 — 중재 규칙

여러 신호가 겹치면 마스킹으로 둘 다 식별 불가가 된다. 현재는 접근·진입·경계음이 겹칠 수 있다.

| 규칙 | 값 | 근거 |
| --- | --- | --- |
| 최소 간격 | 0.12 s | 두 신호가 하나로 들리지 않을 최소 분리 |
| 상위 채널 선점 | 간격 안이라도 허용 | 경고가 밀리면 안 됨 |
| alarm 억제창 | 0.4 s | 경고 직후 하위 채널 차단 |
| state 정숙 요건 | 2 s | 다른 채널이 최근에 울렸으면 보류 |
| `answer` 큐잉 | 하지 않음, 최신만 | 스위프를 빠르게 움직이면 응답이 밀린다 |

이 값들은 검증된 지각값이 아니라 공학적 시작값이다. `SpatialRayProbe`의 step 0.25–0.5 m와 같은 지위다.

### 구현 상태

`SignalArbiter`로 구현했다(`1de2547`). `MonoBehaviour`가 아니고 Unity 시간에 의존하지 않아 EditMode에서 전부 검증된다. 신규 테스트 13개를 포함해 EditMode 26개 전부 통과(2026-08-20).

## 8. P6 — 구현 구조와 이음매

감지 층에서 이미 쓴 패턴을 반복한다.

| 층 | 산출물 | 의존성 |
| --- | --- | --- |
| 모듈 | `SignalIntent`(id, 채널, 월드 위치, 거리) | 오디오 없음 |
| 중재 | `SignalArbiter` — 우선순위·간격·억제 | 순수 로직 |
| 표현 | `AudioSignalRenderer` / 후속 `HapticSignalRenderer` | `SignalCatalog` 조회 |

모듈은 "무엇을 알리고 싶은가"까지만 만들고 소리를 모른다. `RayBoundaryProbe`가 도시 구현을 모르는 것과 같은 관계다.

### 신호 ID 명명

`<대상>.<역할>` 형식이다.

```
region.sidewalk.state
region.road.proximity
region.curb.transition
probe.hit.curb
probe.miss
bounds.study.alarm
```

module ID와 같은 원칙으로 클래스명이 바뀌어도 유지한다. 분석 데이터가 이 ID를 참조한다.

### 카탈로그를 에셋으로 빼는 이유

`SignalCatalog`를 ScriptableObject로 둔다. 음색이 실험 변수가 되고 revision을 로그에 남길 수 있다. 현재는 톤 생성이 모듈 안 리터럴이라 `ModularImplementationAndExperimentPlan.md` §5가 요구하는 "각 module의 설정 snapshot"을 남길 대상 자체가 없다.

**계획 문서 §5의 재현성 필드에 `signal_catalog_revision`을 추가해야 한다.**

### signal_emit 로그

모든 발화 시도를 중재 결과와 함께 기록한다. **현재 로그는 "무슨 일이 일어났는가"만 남기고 "무엇이 실제로 들렸는가"는 남기지 않는다.** 중재로 차단된 신호가 생기면 둘은 달라지고, 인지 실험 분석에서 이 차이는 치명적이다.

## 9. P7 — 기존 `semantic.audio` 처리

| 선택지 | 내용 | 판정 |
| --- | --- | --- |
| 1 | `Configure`에 bus를 추가하되 `SemanticAudioGuide`는 사용하지 않음 | **채택** |
| 2 | `SemanticAudioGuide`도 bus로 이관 | 보류 |

선택지 1을 택한 이유는 `semantic.audio`가 이미 EXP-SWEEP-01의 조건 A(baseline)로 지정되어 있기 때문이다. 지금 손대면 baseline이 흔들리고, 계획 문서 §327의 병합 게이트("기본 상태에서 현재 음향 동작 유지")를 지킬 수 없다.

**따르는 제약**: 한동안 두 가지 신호 문법이 공존한다. 조건 A와 B를 동시에 켜는 profile에서는 사용자가 두 문법을 함께 배워야 하므로, **그런 조합 profile은 당분간 만들지 않는다.**

이관은 나중에 `semantic.audio.v2`를 별도 module ID로 만들 때 수행한다. 그러면 구 버전과 신 버전이 같은 실험에서 비교 가능한 조건이 된다.

## 10. P8 — 검증: EXP-SIG-00

씬 없이 클립만 무작위 재생하고 사용자가 라벨을 답하는 혼동행렬 테스트다.

| 항목 | 게이트 |
| --- | --- |
| 범주 식별 정확도 | ≥ 90% |
| 임의 쌍의 혼동률 | ≤ 5% |
| 채널 역할 식별 | ≥ 95% |
| 방위 정위 오차 | 별도 측정, 기준은 실측 후 설정 |

**이 실험은 EXP-SWEEP-01보다 앞에 온다.** 통과하지 못하면 "공간 형태를 못 읽었다"는 결과가 나와도 신호 혼동 때문인지 공간 인지 실패인지 구분할 수 없다. 계획 문서 §9의 실험 순서에 이 단계가 빠져 있으므로 추가해야 한다.

EXP-SWEEP-00(계산과 표현 검증)과는 병행 가능하다. 서로 다른 것을 검증하기 때문이다. EXP-SWEEP-00은 ray hit 참값과 들리는 위치의 일치를, EXP-SIG-00은 신호 자체의 변별을 본다.

## 11. 구현 순서

브랜치: `infra/feedback-signal-bus`, 기준은 `infra/feedback-experiments`.

기준을 main이 아니라 infra로 잡은 이유는 신호 버스가 fb-01 기능이 아니라 공통 기반이고, `FeedbackModule`의 토글 lifecycle이 infra에 있으며, sweep 코드가 없어 diff가 섞이지 않기 때문이다.

| # | 커밋 | 상태 |
| --- | --- | --- |
| 1 | `SignalIntent`·`SignalChannel`·`SignalArbiter` + 테스트 | **완료** `1de2547` |
| 2 | `SignalCatalog`·`ISignalRenderer`·`AudioSignalRenderer` | 예정 |
| 3 | `FeedbackContext` 도입, `Configure(context)`로 시그니처 일원화 | 예정 |
| 4 | bus를 coordinator에 연결, `signal_emit` 로그 | 예정 |

3번을 뒤에 두는 이유는 `Configure` 시그니처를 한 번만 바꾸기 위해서다. bus가 존재한 뒤에 context를 만들면 두 번 바꿀 필요가 없다. `Configure(context)`는 계획 문서 §121이 이미 명시한 계약이다.

fb-01은 이 브랜치가 병합된 뒤 rebase하고, 그때 sweep의 `answer` 채널 렌더러를 붙인다. 현재 sweep에 오디오가 없으므로 충돌할 표현 코드가 없다.

## 13. 미해결
